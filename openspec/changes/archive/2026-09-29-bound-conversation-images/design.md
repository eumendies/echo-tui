## Context

`read_files` 的单图 5 MB、单次调用总图 10 MB 限额只对一次工具执行有效；`user` / `tool_result` 的 `attachments` 存入 transcript 后，各 provider 转换器会再次发送活跃历史中的图片。`runCompaction` 当前估算 `record.text`，不计算图片；`generateCompactionSummary` 会把被压缩区间原样送给 provider。即使后续正常请求最终能够压缩，摘要请求仍可能先被图片拖垮。已有压缩以 `activeStartIndex` 保留完整 append-only 历史，并保护 tool call/result 配对。

## Goals / Non-Goals

**Goals:**

- 在任何普通或压缩摘要 provider 请求发出之前限制其中图片附件的总二进制体积，默认 10 MB（所有活跃来源合计），并把图片成本纳入压缩时机估算。
- 将 `read_files` 默认单图/单次调用图片附件额度收紧至 3 MB / 6 MB，同时不影响显式配置的限额或已有历史附件。
- 未超预算时保持原 provider 投影与追加式前缀；需要省略时先通过已有压缩减少旧历史，再按需限制实际请求副本。
- 保持本地 transcript、压缩索引、工具配对以及重读图片所需的路径/文本信息完整。

**Non-Goals:**

- 不修改 `read_files` 的工具参数、显式覆盖限额机制或图片编码方式，不提供图片 OCR、语义摘要或每轮固定图片数量窗口。
- 不承诺 provider 的图像 token 精确计量、特定服务商的缓存命中或解决所有与图片无关的网络超时。
- 不把历史文件绝对路径无条件暴露给 provider；只保留原工具输出已有信息。

## Decisions

1. **两类预算分开计算。** 图片上下文估算使用保守的、可测试的每图近似 token 成本，兼容现有 `usageInputTokens` 锚点：锚点后的新图片按增量补记，压缩或修改投影后使锚点失效；历史图片没有锚点时也必须计入。另对实际发送附件采用总二进制字节硬上限 10,000,000；依据有效 base64 数据计算实际二进制字节数，不信任历史附件中可能错误的 `sizeBytes`。请求准备应在序列化为 data URL 前完成预算决策，避免用 base64 文本字符数估算模型视觉 token。预算覆盖用户图片与工具结果图片，普通请求和摘要请求一视同仁。`read_files` 默认单图上限下调至 3,000,000 字节，单次聚合上限下调至 6,000,000 字节；与请求级 10,000,000 字节预算彼此独立，且允许显式传入的工具限额继续生效。
2. **先压缩，再请求侧兜底。** 普通流程先用图片感知估算决定是否触发已有 `runCompaction`；其生成摘要前，按相同硬上限构建*发送副本*，优先保留较新的图片并按原顺序返回。不得改变原始 `compactedRecords`。自动压缩完成后重新核算普通请求；如果摘要为空、无有效边界或活跃区间仍超预算，则对本次 provider 请求副本应用相同兜底。手动 `/compact` 也遵守摘要预算。只在超过阈值/上限时改变投影，不做逐轮常规裁剪。
3. **省略是附件级而不是记录级。** 删除发送副本中较老图片附件时，保留 `tool_call` / `tool_result`、调用 ID、原文本和 `extension`，为受影响的模型可见消息追加简短说明，明确本次未附带该图片；若有原始路径提示可通过 `read_files` 再读。不得仅把 `image_attached: true` 留给模型而不告知已省略；无路径的用户图片仅说明无法从本地重读。不写回持久化记录、不增加持久化字段。摘要仍用已有原生 provider 转换器，输入仅是限定过附件的记录副本，而非拍平历史。
4. **保持跨 adapter 的单一决策入口。** 预算和请求副本由共享上下文层构建，OpenAI Responses/Chat、Codex、Anthropic 复用已有转换器；避免在各转换器各自做不同的过滤。`prompt_cache_key`、会话身份、原始记录顺序与未修改部分前缀均保持不变。必要时为本次请求准备结果提供局部观测信息（省略数量和字节），但不把局部注释回写历史。

备选方案：每轮固定保留最近 N 张简单但在窗口频繁移动时重写缓存前缀；无限制提高 timeout 或只压小单图仍无法解决累计历史；仅依靠 `/compact` 无法保护摘要请求及无有效边界场景。因此不采用。

## Risks / Trade-offs

- **[省略像素损失上下文]** → 向模型说明并保留重读路径，原始附件保留在本地历史；用户原生图片无路径时如需细节须再次上传。
- **[前缀改变带来缓存损失]** → 未超预算不改写、尽量压缩旧历史而非逐轮裁剪；不能承诺省略仅造成一次未命中，持续超预算时可能反复改变前缀。
- **[图片 token 成本因模型而异]** → token 仅用于提前压缩；实际请求由独立字节硬上限保证。配置上限不能被摘要请求绕过。
- **[单次恰好 10 MB 仍可能超时]** → 默认值仅是客户端约束，不代表任意 provider 的 SLA；通过观测真实请求体积、耗时和错误，后续调低默认值或开放用户配置。超时若发生在本地 sharp 解码则需另行处理。
- **[附件元数据错误或 provider 重组差异]** → 对有效 base64 数据计算真实预算并测试四种 adapter 的消息顺序、工具配对和说明文本。

## Migration Plan

无需迁移 journal 或改动原工具 schema；恢复旧会话时在发请求前同样应用预算。新默认工具额度只影响之后新读取的图片，已有附件保持不变。发布后验证包含大量历史图片的恢复会话、自动/手动压缩与工具续接；如回滚则恢复原工具默认额度并移除请求侧预算逻辑，原始历史记录无需修复。

## Open Questions

- 10 MB 是否足以覆盖用户当前使用的 provider 超时场景？实施前后用实际请求图片字节数和请求耗时校准，不把这个数视为已实测的安全上限。
- 是否提供用户配置项及按 provider 区分默认值？首版固定默认值并允许内部注入覆盖以便测试/部署校准，若用户确有需要再设计配置界面。
