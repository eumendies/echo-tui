## Context

现有渲染层以 `charWidth()` 和 `displayWidth()` 计算换行、补齐与光标位置；它将未特别处理的控制字符按一列计算。终端实际输出 Tab 时会依据当前物理列跳至下一个制表位，因此同一行的布局计算和真实输出不一致。问题同时影响 composer 投影和用户 transcript block。

## Goals / Non-Goals

**Goals:**

- 让渲染输出不包含会由终端自行解释的 Tab。
- 使用与输出一致的可见宽度计算、换行和光标列位置。
- 保留 composer state、transcript record 与 provider 请求中的原始 Tab。

**Non-Goals:**

- 不改变 Tab 在输入编辑模型中的字符单位语义。
- 不支持用户可配置的终端制表位。
- 不重构 Markdown、表格等与本缺陷无关的渲染系统。

## Decisions

### 在渲染层按固定制表位展开 Tab

新增共享的 Tab 展开能力，将 Tab 替换为到下一个固定制表位所需的空格，并在计算显示宽度、自动换行与写出行文本时使用同一规则。固定为八列，与常见终端默认值一致。

备选方案是把 Tab 统一替换为四个空格再写入 composer。这会改变用户提交文本，且无法反映 Tab 相对于前缀和当前列的位置，因此不采用。

### 保持数据层原文，仅投影时规范化

`ComposerState` 和 transcript 继续保存 `\t`；渲染函数根据当前行起始列展开它。这样模型仍收到原始堆栈或代码，持久化会话也不发生不可逆改写。

### 优先覆盖普通文本渲染路径

先接入 `layout.ts` 的 composer 与通用换行能力，以及 `blocks.ts` 用户消息路径。这两条路径正是可见缺陷所在。共享宽度函数同时为其他调用方提供正确结果；与 Markdown 表格等独立路径的 Tab 行为留在后续单独评估，避免扩大修复范围。

## Risks / Trade-offs

- [固定八列与少数终端自定义制表位不同] → 输出使用空格而非实际 Tab，确保 TUI 自身布局稳定。
- [Tab 展开改变光标可见列] → 使用同一共享逻辑更新光标位置，并以回归测试覆盖。
- [遗漏独立渲染路径] → 用共享 API 替换本缺陷涉及的路径，并在测试中验证 composer 和用户 block 的行宽。

## Migration Plan

该变更不涉及数据迁移。发布后，已有会话中的原始 Tab 在下一次重绘时自动获得稳定投影；若出现回归，可回退渲染层改动，不影响已存储的 transcript 内容。
