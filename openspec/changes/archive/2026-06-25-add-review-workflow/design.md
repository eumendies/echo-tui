## Context

当前内置 workflow 机制已经能把 slash command 转换为带专用 prompt 和 metadata 的普通 assistant turn，并支持参数策略及 plan-to-normal mode 策略。`/review` 不需要新的 runtime，但其 prompt 必须稳定约束审查范围、验证门槛和输出格式，否则模型容易报告未经确认的猜测、关注无关存量代码，或给出大量低价值风格意见。

“当前代码变更”默认指 Git 工作区相对 `HEAD` 的 staged、unstaged 和 untracked 变更。review 需要先建立完整变更清单，再读取必要的上下文和调用方；仅看 diff 片段不足以确认问题。对于可执行验证，workflow 可以运行与候选问题直接相关的测试、类型检查或只读诊断，但不得修改源代码或使用 `apply_patch`。

## Goals / Non-Goals

**Goals:**

- 提供纯 `/review` 内置命令，审查当前工作区变更。
- 按正确性、架构、代码风格的顺序寻找候选问题。
- 对每个候选 finding 进行针对性验证，证据不足则丢弃。
- 使用稳定严重级别，并按严重级别从高到低输出。
- 复用现有 workflow handler、mode 切换、agent loop 和工具系统。

**Non-Goals:**

- 本次不支持 `/review <path>`、commit range、PR URL 或远端分支参数。
- 不实现自动修复、自动提交、独立 review UI 或结构化 finding 存储。
- 不要求穷尽所有缺陷，也不把缺少测试本身默认视为 finding。
- 不报告与当前变更无直接关系的存量问题、纯偏好或无明确影响的 nit。

## Decisions

### 1. `/review` 作为无参数内置 workflow

新增独立 `review-workflow.ts`，定义 prompt factory 和 `AgentWorkflowDefinition`，并把 definition 加入现有 `BUILT_IN_AGENT_WORKFLOWS`。命令使用 `argumentPolicy: "none"`，首版只审查当前工作区，避免提前设计 scope、revision 和 provider 参数协议。

备选方案是复用 project skill。该方案会使 `/review` 可被禁用或同名覆盖，也无法保证产品级的验证和输出语义，因此不采用。

### 2. 从 plan mode 切换到 normal，但 workflow 保持只审查

`/review` 使用 `switch_plan_to_normal`。虽然读取 diff 可在 plan mode 完成，但验证候选问题可能需要运行测试、类型检查或项目特定诊断，这些命令不都属于 plan mode 的 readonly bash allowlist。

normal mode 只扩大可用验证工具，不授权 workflow 修改代码。prompt 明确禁止 `apply_patch`、写文件命令、格式化器和自动修复命令。mode 切换继续沿用现有持久语义，不在 workflow 完成后恢复。

### 3. 以 `HEAD` 为默认基线并覆盖三类工作区变化

workflow 首先使用 `git status --short`、`git diff`、`git diff --cached` 和必要的文件读取识别 staged、unstaged、untracked 变更。对 untracked 文件直接读取内容；对 rename、delete 和新增文件保留其变更语义。若当前目录不是 Git 仓库或没有可审查变更，明确说明并结束，不臆造 review 范围。

只审查当前变更引入或暴露的问题。允许读取未修改调用方、测试和配置来验证影响，但不得把其中无关的既存缺陷作为 finding。

### 4. 两阶段审查：候选发现后再验证

第一阶段按以下顺序生成候选问题：

1. 正确性：行为错误、回归、边界条件、错误处理、安全性、数据损坏和与需求不符。
2. 架构：职责边界、状态所有权、层间依赖和重复机制造成的具体风险。
3. 代码风格：仅检查违反仓库明确约束或显著降低可维护性的具体问题。

第二阶段逐项验证候选问题。验证至少需要：

- 定位到当前变更中的具体文件和最小行范围。
- 阅读足够上下文、调用方、类型、配置或测试，建立可触发路径。
- 在适用且成本合理时运行最小针对性验证。
- 确认问题由当前变更引入或直接相关，并描述实际影响。

无法建立触发条件、只能表达可能性、依赖未知外部假设或仅属个人偏好的候选项必须丢弃。测试失败只有在能归因于当前变更时才可报告。

### 5. 使用 P0-P3 严重级别和固定 finding 结构

严重级别定义为：

- `P0`：会造成灾难性、广泛且必须立即阻断的后果，例如明确的数据破坏或严重安全事故。
- `P1`：高影响正确性问题，会使核心功能在现实条件下失败或产生严重回归。
- `P2`：中等影响的局部正确性、可靠性或架构问题，应在合入前修复。
- `P3`：低影响但已经验证、具有明确维护成本的架构或仓库规范问题；不包含纯 nit。

每个 finding 包含标题、严重级别、精确位置、触发条件、验证证据和影响。最终结果按 P0、P1、P2、P3 排序；同级优先正确性，再按影响和证据强度排列。finding 之外可附简短的检查范围和验证命令摘要，但不得用大量一般性建议稀释问题列表。

### 6. 空结果优于推测性输出

如果验证后没有候选项达到报告门槛，workflow 明确输出“未发现可确认问题”，并可简要列出已检查范围。不得为了保持输出丰富而降低置信度、报告测试缺失、建议重构或提出风格偏好。

## Risks / Trade-offs

- [低误报策略可能漏掉真实缺陷] → 明确这是预期取舍；先扩大证据收集，再提高单个 finding 的确认度，而不是降低报告门槛。
- [模型可能运行过宽或有副作用的验证命令] → prompt 要求选择最小针对性验证并禁止写文件、格式化、自动修复和 `apply_patch`；高风险命令仍受现有审批保护。
- [Git 工作区包含生成文件或超大 diff] → 先读取 status 和 diff stat，按风险与依赖关系聚焦检查；无法完整覆盖时在结果中说明范围，不把未检查内容描述为已验证。
- [严重级别在不同项目间理解不一致] → 在 prompt 中内置 P0-P3 定义，并要求根据实际影响而非代码复杂度定级。
- [架构和风格 finding 容易主观化] → 仅在存在仓库明确约束、可证明的职责破坏或具体维护风险时报告，否则丢弃。
